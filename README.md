## AAA - Authentication Authorization Accounting

Описание механизма аутентификации и авторизации.

Механизм спроектирован так, чтобы не хранить ключи пользователей устройства на удаленном сервере, 
ответственность за хранение и распространение ключей доступа несет только сам пользователь.

Реализация имеет 2 роли:
- **Админ**, может создавать пользователей и других админов.
- **Пользователь**, не может создавать других пользователей,
  пункты доступа(настройки, дебаг и т.п.) определяются при создании, может быть ограничен по времени действия.

### Админ

Технически - обладатель приватного асимметричного ключа - `PrivateKey`.  
Ключ создается случайным образом во время активации устройства.  
Хранится на устройстве администратора, публичная часть ключа передается в устройство.  

Распространять приватный ключ необходимо с особой осторожностью.

### Пользователь(сертификат)

Технически - подписанные приватным ключем данные пользователя + соль, в дальнейшем просто "сертификат".  
Полная структура сертификата: {`ПОДПИСЬ`, `СОЛЬ`, `ДАННЫЕ_ПОЛЬЗОВАТЕЛЯ`} - `UserCert`.  
`ДАННЫЕ_ПОЛЬЗОВАТЕЛЯ` - TLV структура, которая в свою очередь содержит:
- Serial устройства, для которого он предназначен.
- Имя пользователя.
- Права пользователя.
- Временные ограничения, напр. диапазон дат по которые он может быть использован.

`СЛУЧАЙНОЕ_ЧИСЛО` - `salt`, должно быть достаточно большим чтобы гарантировать уникальность, напр. 128бит.  

`ПОДПИСЬ` - подпись асимметричным приватным ключем(`PrivateKey`) на `СОЛЬ` + `ДАННЫЕ_ПОЛЬЗОВАТЕЛЯ`.  

#### Активация

Активация - генерация и установка ключей, с помощью которых в дальнейшем будут 
создаваться и проверяться пользователи(сертификаты).

- Клиент(телефон) проверяет возможность активации устройства [auth->status](./bluetooth-api.md).
- Клиент генерирует пару асимметричных ключей.
- Публичный ключ записывается в устройство [auth->activate](./bluetooth-api.md).
- Приватный ключ (`PrivateKey`) сохраняется в защищенное локальное хранилище.

#### Алгоритм прохождения ААA

Процесс проходит одинаково что для админа, что для пользователя.  
В случае админа, ему для АА необходимо создать пользователя(сертификат) со всеми правами.  

Для АА необходимо:
- Установить сопряжение (без bonding), нужно для шифрованной сессии.
- Убедиться что устройство готово к AAA - [auth->status](./bluetooth-api.md).
- Записать в характеристику [auth->auth](./bluetooth-api.md) сертификат.
- Сертификат должен успешно пройти верификацию подписи по данным сертификата.
- Если сертификат используется в первый раз, то необходимо установить ключ идентификации устройства.
- Если сертификат уже использовался, то необходимо пройти проверку идентификации устройства.

**Установка ключа идентификации устройства**

Необходимо для защиты от кражи сертификата, т.е. сертификат привязывается к первому использовавшему его устройству.  

- Клиент(телефон) должен сгенерировать пару асимметричных ключей идентификации.
- Записать публичный ключ в устройство [auth->identity-key](./bluetooth-api.md).
- Сохранить приватный ключ в защищенное локальное хранилище.

О необходимости установки ключа идентификации можно узнать из [auth->status](./bluetooth-api.md).  
Без данной процедуры AAA не считается завершенной: 
права применены не будут, сертификат не будет считаться использованным.

**Проверка идентификации устройства**

- Клиент(телефон) читает случайное число из [auth->identity-challenge](./bluetooth-api.md) - `challenge-data`.
- Подписывает его своим приватным ключем идентификации.
- Записывает подпись в [auth->identity-challenge](./bluetooth-api.md).
- устройство верифицирует подпись, если успешно - проверка пройдена.

#### Проверка ограничений и удаление пользователей

Устройство всегда должно приблизительно знать текущее время, чтобы валидировать временные ограничения ключа.  
Для этого необходим RTC + синхронизация с телефоном (предусмотреть защиту от подмены времени).  
Таким образом при использовании ключа с временным ограничением достаточно просто проверить 
попадает ли текущее время в диапазон времени действия данного ключа.  

**Удаление пользователя** может быть осуществлено только админом.  
Удаление происходит по типу черного списка, в NVM устройства создается запись не принимать такой ключ.  
Список ключей-пользователей можно прочитать из самого устройства, если этот ключ в нем использовался, из файла ключа, который был сгенерирован.  
Для большего удобства можно в телефоне администратора хранить все ранее сгенерированные ключи.

#### Ротация мастер-ключа

Смена приватного ключа, которым админ(ы) создают сертификаты.  
Проходит в два этапа:
- Установка нового ключа, старый переход во второй слот, работают оба.
- Удаление старого ключа.

На первом этапе удаляются все отозванные сертификаты старого ключа из памяти nokey.  
На втором этапе БЕЗВОЗВРАТНО удаляются все, в т.ч. НЕ отозванные сертификаты старого ключа.  

#### Сброс

Если файл с ключем пользователя утерян и нет возможности его удалить, то можно прибегнуть к сбросу исходного ключа, это может сделать только админ.  

Если утерян админ, то можно прибегнуть к аппаратному сбросу (зажав надолго кнопку на плате), 
для этого нужен физический доступ к плате.
